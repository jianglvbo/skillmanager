# 提炼执行器

---

## Default Stance

### 核心原则

- **两步模式**：先出方案报告供用户审阅，确认后再执行。绝不跳过方案直接创建文件
- **方案报告用「内容卡」结构**：每个拟产出条目一张卡，五段 emoji（📥提炼什么／📤提炼成什么／✅质量自评／💡我的建议／⚠️待你定）+ 顶部总览表；替代旧版字段横表
- **可读性优先**：正文保留原文的比喻、案例、推理链条和生动表达。用自然语言段落而非干巴巴的要点罗列
- **忠实原文**：可重组表达、优化结构，但绝不捏造、编撰、偏离原文事实。比喻和案例必须来自原文
- **简体中文产出**：框架条目正文一律用简体中文。若原始资源仍为繁体（粗加工遗漏），提炼时作兜底繁转简，仅字形转换、不改用词语气
- **标签来自标签体系，与文件夹分类互补**：标签捕捉文件夹无法表达的跨维度信息，允许跨分类引用（如投资心得文件可标分析框架标签）。市场/行业标签仅在内容确实仅限特定市场/行业时添加，通用心得不强制绑定。标签宁精勿滥，不自造标签
- **条目间关联**：仅指同源多条条目之间的逻辑关联，在方案报告中标注关联方向；跨 vault 的关联备注在审查阶段处理。**提炼阶段不在文件中创建任何关联章节**——既不输出 `## 关联` 章节，也不输出空脚注占位。条目间关联的正式落地是审查阶段写入文末 `---` 脚注区的关联脚注（`[^enhance-N]`/`[^complement-N]` 等，见 footnote-taxonomy.md）
- **模板驱动**：执行时每个条目必须使用对应分类的模板填写 frontmatter + 正文
- **参数全部由编排者传入**：缺参即报错

### 禁止行为

- 绝不跳过方案报告直接创建框架条目
- 绝不在"我的"层创建或修改文件
- 绝不遗漏博主行的处理（如涉及已登记博主，必须同时更新博主档案）
- 绝不将非投资内容放入"其他"层
- 绝不使用标签体系外的标签
- 绝不捏造、编撰原文没有的内容——比喻和案例必须来自原文
- 绝不在方案文件用 `#N` 表示编号（会被 Obsidian 识别为 tag），博主编号统一「编号N」写法
- 绝不把 checkbox 写在 `>` 引用块或行内（须顶层 `- [ ]` 列表项，否则不渲染勾选框）
- 绝不在粗加工/提炼时自动将未登记作者「补登」进博主控制台——未登记作者其条目归「其他」层，且**绝不就「是否补登」询问用户**（见 framework-rules #12）

## Workflow

### 前置条件（由编排者保障）

本 skill 的输入必须来自 `工作区/原始资源/` 且 `status=待提炼`。编排者需在调用前确认：

- 原始资源中已存在该文档且 `status=待提炼` → 直接进入本 skill 两步模式。
- 原始资源中**不存在**该文档（无 `status=待提炼` 记录）→ 说明仍在 `工作区/粗制品/`，编排者应先调用 `investment-coarse-processor` 粗加工（置 `status=待提炼`），再进入本 skill。**本 skill 不处理粗制品。**

### 第一步：提炼分析 → 生成方案报告

读取原始资源全文，分析内容后生成提炼方案报告。

**报告用「内容卡」结构（Markdown，非 HTML）**，替代旧版字段横表——每张卡五段，目的是让用户快速读懂内容、看清质量、做出选择。

**顶部总览表**（轻量）：篇 → 拆几条 → 核心主题 → 归属层。

**内容卡模板**（每拟产出条目一张）：

```markdown
### 条目 N ｜ {建议标题}

📥 **提炼什么**：{原文核心素材摘录 + 出处（[[原始资源/xxx]] 章节）}
📤 **提炼成什么**：归属层 {我的/博主/其他} ／ 分类 {投资心态…} ／ 一句话摘要 {…}
✅ **质量自评**：原文支撑度 {强/中/弱} ／ 引申风险 {…} ／ 时效判断 {长期有效/短期} ／ 库内关系 {新增·互补·重复预警→[[已有条目]]}
💡 **我的建议**：{拆不拆、归哪类——内容驱动建议，非强制}
⚠️ **待你定**：{开放问题 / 标签选择 / 重叠决策}
```

报告设计原则：

- 内容卡式，每个条目一个独立区块，五段 emoji 结构一目了然
- 顶部总览表先让用户把握全局（几篇、拆几条、主题、归属层）
- 标签必须来自标签体系（investment-framework/references/tag-taxonomy.md），允许跨分类引用；通用心得/心态不强制加市场/行业标签
- 库内关系栏标注与已有条目的 新增/互补/重复 关系，重复时给 wikilink
- ⚠️ **归属层铁律**：作者必须在博主控制台已登记才能用「博主」层；未登记一律「其他」层，且 Agent 绝不自动补登、绝不就此询问用户（见 framework-rules #12）
- 便于批改：用户可直接回复"条目1标题改为XX"、"条目2不要了"、"条目3归到交易体系"

### 方案交付方式（对话直出 vs 文件化）

提炼方案按体量自动选交付方式：

- **对话直出（默认·单篇/少量）**：方案报告直接输出到对话中，用户回复"确认 / 改XX / 不要了"即可，不写文件。
- **文件化 + 决策区（批量「提炼所有」）**：默认把方案写入 vault `{PROPOSAL_DIR}/YYYY-MM-DD-提炼方案.md`，用户在 Obsidian 里勾选决策。

**文件化模式规范**：

1. 文件顶部置「⚙️决策区」：用标准顶层 `- [x]` task 列出所有待定项并预勾我的建议（建议项默认勾上）。
2. 正文为内容卡（见上方模板），**只做展示、不含 checkbox**，避免污染阅读。
3. 交互闭环：用户勾选（不动=用建议；取消我的勾+勾别的=改）→ 回对话说「执行提炼」→ 助理 Read 该文件、解析决策区 `[x]` 项作为确认依据落地。

**Obsidian 格式坑（必须规避）**：

- `#N` 会被识别为 tag，博主编号改用「编号N」写法（如「令狐不败，编号43」），绝不用 `#43`。
- checkbox 必须是顶层 `- [ ]` 列表项；写在 `>` 引用块内或行内（无 `- ` 前缀）会失效、不渲染勾选框。
- HTML 仅用于定稿后存档汇报，方案阶段一律用 Markdown。

### 第二步：用户确认 → 提炼执行

**对话直出模式**：用户审阅后——直接确认 / 提出修改 / 取消。
**文件化模式**：用户勾完决策区回「执行提炼」，助理 Read `{PROPOSAL_DIR}/...` 解析决策区 `[x]` 项作为确认依据。

确认后执行：

1. 按方案中的归属层和分类确定文件路径
2. 选择对应模板（从编排者传入的 templates）
3. 创建文件，填写 frontmatter + 正文内容。正文按模板中的写作指引，保留原文的比喻、案例、推理链条，用自然语言段落而非干巴巴的要点罗列
4. 条目间关联在方案报告（对话）中标注方向即可，**不在文件中创建 `## 关联` 章节或空脚注占位**。该关联的正式落地是审查阶段写入文末 `---` 脚注区的关联脚注（`[^enhance-N]`/`[^complement-N]` 等，见 footnote-taxonomy.md）。仅当正文确有具体数据/时效判断时，提炼阶段才输出 `---` 脚注区并填 `[^data-N]`/`[^date-N]`（脚注区以 `---` 分隔线标识，无 `## 脚注` 标题）
5. 如涉及已登记博主，读取 `博主/{博主名}/{博主名}.md`，在信息汇总章节追加本次条目
6. 如涉及宏观事件：通用宏观框架放 `宏观/`，博主的具体宏观分析放 `博主/{博主名}/宏观/`，填写 `event` 字段以便跨博主聚合，并在传导路径中关联行业/个股 wikilink
7. 将原始资源文件的 status 改为 `已提炼`

## 自检

- [ ] 源文件是否在原始资源中且 `status=待提炼`？若否，是否已先从粗制品完成粗加工？
- [ ] 方案是否已交付（对话直出 / 写入 `{PROPOSAL_DIR}`）供用户审阅？
- [ ] 用户是否已确认方案（或提出修改）？
- [ ] 产出正文是否为简体中文（若原始资源为繁体，是否已兜底转换）？
- [ ] 每个条目的标签是否来自标签体系？
- [ ] 每个条目是否使用了正确的模板？
- [ ] frontmatter 是否完整且规范？——`author` 必填；字段顺序符合所属分类模板 canonical（标准 `title→createDate→updateDate→author→tags→source`，见 framework-rules #27）；**无 `date` 字段**（#27 层间边界）；`createDate`/`updateDate` 裸写无引号
- [ ] 如涉及博主，博主档案是否已更新？
- [ ] 归属层是否合规？未登记作者是否归入「其他」层（而非博主层、而非被自动补登）？
- [ ] 个股条目文件名是否带股票代码 `{名称}({代码})`（见 framework-rules #28）？代码缺失时是否联网检索、A+H/美股双上市且文章无法区分时是否默认 A 股？
- [ ] 如涉及宏观，传导路径 wikilink 是否已添加？
- [ ] 提炼产出文件是否未含 `## 关联` 章节、未含空脚注占位？（条目间关联仅在方案报告中标注方向，正式落地为审查阶段文末 `---` 脚注区的关联脚注）
- [ ] 是否在"我的"层创建了文件？（应该没有）
- [ ] 方案报告是否用「内容卡」结构（5 段 emoji + 顶部总览表）而非旧字段横表？
- [ ] 批量「提炼所有」是否写入 `{PROPOSAL_DIR}` 并含顶部「⚙️决策区」（`- [x]` task）？
