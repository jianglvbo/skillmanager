# 框架边界规则与全局规则

## 框架边界

### 投资心态 vs 投资心得
- 根因是情绪/心理的 → **心态**
- 能靠心态纪律避免的 → **心态**
- 其他有借鉴意义的经验教训 → **心得**
- **没有借鉴意义的直接丢弃**

### 分析框架 vs 交易体系
- 分析方法论、判断框架 → **分析框架**（工具箱）
- 具体买卖条件、执行规则 → **交易体系**（操作手册）
- 两者有交叉时允许交叉引用，各有侧重

### 分析框架内部：方法论 vs 分析档案
- **方法论**：分析方法本身（如"用PE判断企业是否值得买入"）
- **分析档案**：用这个方法论分析具体标的的实例（如"段永平用PE方法分析茅台"）
- 分析档案是方法论的应用案例，通过 wikilink 关联回方法论

## 全局规则

1. 日期格式：原始资源用 `date`（帖子发布日期），框架条目用 `createDate`/`updateDate`（条目创建/更新日期），均用 YYYY年M月D日；tags 中的日期用 yyyy-MM-dd
2. 文件命名：中文，不带日期前缀
3. wikilink：完整路径 `[[目录/文件名]]`，不加 emoji
4. 模板文件统一放在 skill 的 `assets/` 目录（非 vault 内），vault 内不设模板目录
5. 框架是活文档，可持续修改迭代
6. 三大归属层（我的/博主/其他）各自包含完整的六大分类
7. 宏观双层存放：顶层 `宏观/` 存通用宏观框架与分析工具（如美林时钟、经济周期指标）；三大归属层下各自的 `宏观/` 子文件夹存该来源对具体宏观事件的分析。跨博主同一事件通过 frontmatter `event` 字段聚合（如 `event: 美联储加息周期`）
8. 行业不按市场分文件夹，用标签区分
9. 个股按市场（港股/A股/美股）分文件夹
10. 博主层按博主名字建子文件夹，档案文件放在该文件夹根目录，按需创建不预建空文件夹
11. 博主的分析框架下有方法论/和分析档案/两个子文件夹；我的和其他的分析框架下不设子文件夹
12. 博主归类仅限博主控制台已登记的博主
13. "其他"层只接收投资相关、来自具体投资人的内容；与投资无关的信息直接丢弃
14. 跨层查找靠 frontmatter 标签，不靠文件结构
15. "我的"层由用户自己管理，Agent 不维护
16. 没有借鉴意义的信息直接丢弃，不入库
17. Tags 规则：精简、分级、有用
    - 只加对分类检索有帮助的标签：个股名称、行业、板块、市场
    - 禁止加无分类价值的标签（如 #RIO、#威士忌 等产品名/品牌名）
    - 用 "/" 做多级分级：行业/食品饮料/白酒、行业/食品饮料/葡萄酒、行业/AI与算力/AI应用
    - 个股文件 tags 示例：[百润股份, 行业/食品饮料/白酒, 市场/A股]
    - 行业文件 tags 示例：[行业/农林牧渔/畜牧业, 市场/A股]
    - 宏观文件 tags 示例：[美联储, 货币政策, 2026-07-03]
18. 可读性优先：提炼产物要让读者快速理解、判断是否有用、记住核心观点。两个层面：
    - **修辞层面**：保留原文的比喻、案例、推理链条和生动表达，不做干巴巴的要点罗列。目标是让经验知识有"血肉"、可理解，而非只剩骨架
    - **认知锚点**（帮读者快速建立理解框架）：
      - **一句话核心判断**：正文开头用一句话浓缩全篇精髓，让读者3秒内决定要不要深读
      - **适用条件/边界**：显式标出这个经验在什么条件下成立、什么条件下不成立。没有边界的经验等于鸡汤
      - **反直觉点**：如果原文有"大家以为X，其实是Y"的认知冲突，在开头把张力拎出来
      - **时间敏感性**：标注经验产生的市场环境和时间背景，帮助读者判断是否还适用
19. 忠实原文：可以重组表达、优化结构、补充上下文说明，但绝不捏造、编撰、偏离原文事实。比喻和案例必须来自原文或原文引用的真实来源
20. 脚注体系：三类脚注（关联/数据溯源/时效标注），定义、格式、添加阶段和位置详见 `references/footnote-taxonomy.md`。提炼阶段可加 `[^data-N]`（数据溯源）和 `[^date-N]`（时效标注）；关联脚注（enhance/supplement/conflict/complement）仅在审查阶段添加。**提炼阶段文件不含 `## 关联` 章节，也不含空 `## 脚注` 占位**（关联脚注在审查阶段随 `## 脚注` 一起写入）
21. Frontmatter 引号规则：YAML 值的外层包裹必须根据值内引号情况切换，否则 Obsidian Properties 面板解析异常：
    - 值不含引号 → 双引号包裹：`title: "珀莱雅深度拆解"`
    - 值含双引号 → 单引号包裹：`title: '周期股投资的"债券+期权"思维'`
    - 值含单引号 → 双引号包裹：`title: "错过'时代'是最大的风险"`
    - 值同时含双引号和单引号 → 双引号包裹+转义：`title: "他说\"好\"了"`
    - **禁止**：双引号包裹的值内部出现未转义的双引号（如 `title: "理解"书""`）
22. 提炼输入必须是原始资源且 `status=待提炼`：提炼（investment-refine）的输入必须来自 `工作区/原始资源/` 中 `status=待提炼` 的文档，**禁止**直接在 `工作区/粗制品/` 上提炼。判断以**原始资源为锚点**——若原始资源中不存在该文档的 `status=待提炼` 记录，说明仍在粗制品，编排者须先调用 investment-coarse-processor 完成粗加工（置 `status=待提炼`），再进入提炼。
23. `source` 字段（框架条目）：YAML 列表（数组），支持多个 wiki 链接值，每项须引号包裹 `"[[...]]"`（避免 `[[` 被 YAML 解析为嵌套序列）。**多个来源统一写入 `source` 数组，框架条目正文不再设 `## 来源` 段落**——来源归口到 `source`，与正文 `## 来源` 段落二选一，现统一用 `source` 数组。
24. 段落布局：Obsidian 渲染要求标题前后有空行分隔，否则 `##` 不会渲染为标题。
    - 每个 `##`/`###`/`####` 标题**前后各需一个空行**（连续两个标题之间只需一个空行）
    - 不同论点/段落之间用空行分隔（连续文本行不超过 3-4 行，超过则分段）
    - 列表项之间、表格行之间不需要空行（保持紧凑）
    - 脚注定义区（`[^id]: ...`）内部不需要空行，但脚注区之前需空行与正文分隔
25. 脚注内联标记：每条脚注定义（`[^id]: ...`）**必须在正文中有对应的内联标记**（`[^id]`），否则 Obsidian 不会渲染该脚注。审查阶段添加关联脚注时，必须同时在正文相关论述处插入 `[^id]` 标记。提炼阶段添加 `[^data-N]`/`[^date-N]` 时同理。禁止出现"有定义无标记"或"有标记无定义"的孤儿脚注。
26. 脚注标题：正文中有任何脚注定义（`[^xxx]:`）时，**必须在该批脚注定义前写 `## 脚注` 标题**，所有脚注定义放在该标题下。没有脚注定义时不写 `## 脚注` section。
27. 加粗标记空格：`**text**` 前后必须与相邻中文字符之间留一个空格（如 `中 **"建设财政"** ——`），禁止 `中**"建设财政"**——` 这种紧贴写法。紧贴会导致部分渲染器不识别加粗，视觉上也无法区分加粗区域与正文。
28. 列表项必须独占一行：每个 `-`/`*`/`1.` 列表项必须从新行开始，禁止多个列表项挤在同一行（如 `段落。- **item1**：...- **item2**：...`）。列表项前需空一行与正文分隔。
