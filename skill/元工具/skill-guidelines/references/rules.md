# 九条工程规律

## 规律一：Description 决定触发

含中英文关键词，明确什么时候不要用。

## 规律二：主文件短，细节下沉

主文件 ≤ 500 行。场景细节/边界/示例 → references/。

## 规律三：工作流必须编号

```markdown
❌ "先读文件，再检查，最后输出"
✅
1. 第一步：读文件校验
2. 第二步：选分支（见 references/routing.md）
3. 第三步：生成输出
```

## 规律四：写清楚默认行为

输入为空？路径未指定？格式未指定？冲突怎么处理？每项都要有答案。

## 规律五：输出格式模板化

不写「输出一个 Markdown」，而是给出完整 frontmatter 模板。

## 规律六：规则有来源

| 优先级 | 来源 |
|:---|:---|
| 1 | 官方文档 / API 规范 |
| 2 | 权威方法论 |
| 3 | 工程实践 |
| 4 | 用户约定 |
| 5 | 最佳实践推断 |

不确定的标记 `[待验证]`。

## 规律七：两种体量都可行

| 体量 | 结构 | 适用 |
|:---|:---|:---|
| 轻量 | 单 SKILL.md | 线性流程、<5 条规则 |
| 标准/重量 | SKILL.md + references/ + assets/ | 多模式、方法论驱动 |

## 规律八：有测试用例

定义「正常输入 → 期望输出」「缺失字段 → 期望报错」「边界 → 期望行为」。

## 规律九：中文用户专节

规定输入语言、输出语言、文件命名、日期格式。
