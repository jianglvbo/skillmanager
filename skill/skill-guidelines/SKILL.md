# Agent Skill 准则

以下是创建和修改 Agent Skill 时必须遵守的八条核心准则。无论是从零设计新 Skill，还是修改已有 Skill，都应以此为准绳。

---

## 准则一：职责单一与模块化

一个 Skill 应该专注于**一个明确的领域或任务类型**，避免试图解决过多松散相关问题的"全能技能"。

- 保持技能精简：每个任务提供 **2-3 个 Skills 模块**时效果最佳，超过 4 个收益显著递减。
- 合理的粒度应类似于**函数**——解决一类明确的任务。
- 单一职责便于测试、版本控制，也避免指令内容过长导致上下文过载。

> ❌ 反例：一个叫 `investment-tools` 的 skill 同时处理行情查询、财报分析、博主追踪、链接收集
> ✅ 正例：拆成 `stock-analyzer`、`link-analysis`、`xq-blogger-analysis` 三个独立 skill

---

## 准则二：精准的描述与语义发现

`description` 是 Agent 决策和选择 skill 的**唯一依据**。描述必须：

- **精确定义适用范围**：这个 skill 管什么、不管什么
- **包含触发关键词**：匹配用户意图的自然语言模式
- **说明独特价值**：与其他 skill 的区别在哪里

像设计 API 一样对待 skill 命名和描述——减少歧义，提升发现效果。

> ❌ 模糊描述：`"帮助处理投资相关内容"`
> ✅ 精准描述：`"雪球博主分析框架的操作手册。覆盖博主画像的粗加工、提炼、问答、回流全流程。触发词：「博主分析」「博主画像」「雪球博主」"`

---

## 准则三：确定性优先与结构刚性

对于需要精确执行、容错率低的脆弱任务，**优先使用脚本、模板或硬性规则**，不依赖 LLM 生成。修改已有 skill 时同样遵循此准则，不因是"小改"而放松结构要求。

- 数据库迁移、生产环境变更等 → 脚本先行
- 通过**编号清单、决策树、显式输出模式**等刚性结构元素，限制和缩小解决方案空间
- 目的：减少生成输出的**随机性和幻觉**

```
✅ 刚性结构示例：
1. 读取输入文件
2. 校验 frontmatter 字段完整性（必须包含 category/content_type/time_sensitivity）
3. 根据 category 选目标目录（见决策树附录）
4. 移动文件到目标目录
5. 验证：确认源目录文件已删除，目标目录文件存在
```

---

## 准则四：渐进式披露与少即是多

不要将 Skill 变成百科文档或塞入大量通用常识。Skill 的价值在于**"经验密度"**——只写 Agent 不知道的特定领域知识。

分层策略：
- **SKILL.md 主体**：核心工作流、关键决策点（必须加载的）
- **references/ 附加文档**：高级用法、边界情况、详细规则（按需读取）
- **scripts/ 脚本**：大型参考数据通过脚本按需查询，不常驻上下文

> **中等长度、聚焦的文档优于全面但冗长的综合文档。**

---

## 准则五：核心知识的人类主导

不要依赖模型自动生成 Skills。核心的程序性知识仍需**人类专家输入**。

- 人类设计的操作手册、风格指南等"**部落知识**"是 Skill 的杠杆支点
- 模型可以帮助格式化、补全、翻译，但方法论和判断标准必须人来定义
- 确保 Agent 能够真正执行并**符合团队规范**，而不是生成"看起来对但做法不对"的东西

---

## 准则六：内置验证循环与可观测性

一个好的 Skill 不仅要让 Agent 生成结果，还要让它**自查**。

- 在执行逻辑中加入**验证循环**：最终输出前检查建议的可执行性、结果的完整性
- 执行过程应具备**日志记录**，支持调试分析和问题定位
- 避免输出充满套话——用检查点确保每一步都真的做了

```
✅ 验证循环示例：
5. 自检：
   - [ ] 输出文件是否包含所有必需字段？
   - [ ] 引用的源文件路径是否有效？
   - [ ] 是否有未闭合的代码块或格式错误？
   → 任一不通过，回溯到对应步骤修正
```

---

## 准则七：安全性与权限边界

Skill 具备真实的执行能力，必须考虑安全治理。

- **限制工具范围**：技能应只使用它需要的特定工具
- **定义权限边界**：对敏感数据强制执行只读模式
- **防止注入风险**：避免过度宽泛的工具访问权限引发数据窃取或提示注入
- 对外部操作（发消息、调 API、写文件到敏感目录）需要显式确认

---

## 准则八：标准化输出与工程化结构

输出格式越明确，结果越稳定。

### 输出规范
- 规定**固定的输出模式**（JSON、特定 Markdown 表格、标准字段集）
- 使结果易于下游消费（被其他 skill 或工具解析）
- 用模板而非自然语言描述输出格式

### 工程化结构（四层分工）

| 层 | 职责 | 形式 |
|:---|:---|:---|
| **自然语言** | 判断与编排 | SKILL.md 核心流程 |
| **脚本** | 稳定执行 | scripts/ 下的确定性代码 |
| **模板** | 规范输出 | assets/ 下的模板文件 |
| **参考资料** | 补充细节 | references/ 下的规则文档 |

---

## 补充：级别分类（辅助判断准则一）

| 级别 | 判断条件 | 最少结构 |
|:---|:---|:---|
| 🟢 轻量 | 单一操作、无分支决策 | `SKILL.md` |
| 🟡 标准 | 3-5 步流程、规则 > 10 条 | + `scripts/` 或 `references/` |
| 🔴 重量 | 多模式路由、方法论驱动 | + `assets/` + `examples/` + `evals/` |

---

## 设计模式速览

- **Request Router**：SKILL.md 开头放路由表，Agent 先判断场景再走对应分支
- **Skill 组合**：复杂流程拆成多个小 Skill，通过触发条件串联成流水线
- **Step-by-step 工作流**：编号清单写核心流程，详细展开放在 references/
