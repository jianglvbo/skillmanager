# Agent Skill 设计纲领：从理论到工程化落地

> 将人类专家知识转化为 AI 可执行工作流的工程化产物。不是提示词拼接，而是一份给 AI 看的、高内聚低耦合的、具备异常处理机制的"微服务架构文档"。

---

## 一、核心定位与认知重构

Skill 绝非简单的 Prompt 拼接。在架构设计中，必须明确 Skill 与周边组件的边界：

| 组件 | 解决什么问题 | 类比 |
|:---|:---|:---|
| **Skill** | "怎么做"——任务编排器，决定何时、如何组织操作 | 微服务的方法 |
| 脚本 (scripts/) | "稳定执行"——确定性逻辑（数据清洗、格式转换） | 微服务的内部函数 |
| 知识库 (references/) | "知道什么"——制度、文档、参考资料 | 数据库 |
| 工具 (MCP/Tool) | "能做什么操作"——原子能力 | 微服务的 SDK/API |

> **Skill 不是脚本**：脚本负责执行，Skill 负责编排。
> **Skill 不是知识库**：知识库解决"知道什么"，Skill 解决"怎么做"。
> **Skill 不是工具**：工具提供"手"，Skill 提供"方法"。

## 二、八大设计原则（战略指导）

原则回答"为什么这样设计"。理解原则后，即使模板记不全，也能做出正确的设计决策。

### 原则一：职责单一与模块化

一个 Skill 专注于**一个明确的领域或任务类型**。合理粒度类似函数——解决一类明确的任务，而非试图成为"全能技能"。

- 每个任务提供 2-3 个 Skill 模块时效果最佳，超过 4 个收益递减
- 单一职责方便测试、版本控制，避免指令过长导致上下文过载
- 复杂流程应拆成多个小 Skill，通过触发条件串联成流水线

> ❌ `investment-tools` 同时处理行情查询、财报分析、博主追踪、链接收集
> ✅ 拆成 `stock-analyzer`、`link-analysis`、`blogger-refine`

### 原则二：精准描述与语义发现

`description` 是 Agent 决策和选择 Skill 的**唯一依据**。像设计 API 一样对待——必须精确、可发现、有边界。

- ✅ 同时包含中英文触发关键词
- ✅ 说明与其他 Skill 的区别（防止误触发）
- ✅ 明确何时**不要**使用（非触发条件）
- ❌ 不要只写模糊的功能描述

> **好例子：**
> `"雪球博主分析框架的操作手册。覆盖博主画像的粗加工、提炼、问答、回流全流程。触发词：「博主分析」「博主画像」「雪球博主」。区别于 link-analysis（只处理链接收集），本 skill 负责链接收集之后的全部加工流程。"`

### 原则三：确定性优先与结构刚性

对容错率低、步骤固定的脆弱任务，**优先用脚本、模板或硬性规则**，而非依赖 LLM 自由生成。

- 编号清单 → 约束执行顺序
- 决策树 / 路由表 → 约束分支选择
- 显式输出模板 → 约束输出结构
- 默认行为定义 → 约束边界场景

> 目的：缩小解决方案空间，减少随机性和幻觉。不确定性是 bug 的来源。

### 原则四：渐进式披露与上下文预算

上下文不是无限资源。Skill 的价值在于"经验密度"——只写模型不知道的特定领域知识，删除教科书式常识。

| 层 | 内容 | 加载时机 |
|:---|:---|:---|
| SKILL.md 主体 | 核心流程、关键决策点 | 始终加载 |
| references/ | 高级用法、边界情况、完整规则 | 按需读取 |
| scripts/ | 确定性执行脚本 | 按需查询 |

> 主文件超过 200 行是危险信号——考虑拆分。中等长度、聚焦的文档优于全面但冗长的综合文档。

### 原则五：核心知识的人类主导

方法论和判断标准必须由人类定义。模型可以帮助格式化、补全、翻译，但**不能替代专家判断**。

- 人类设计的操作手册、风格指南等"部落知识"是 Skill 的杠杆支点
- 不要依赖模型自动生成 Skills，核心的程序性知识仍需人类专家输入
- 确保 Agent 执行结果符合**团队规范**，而非"看起来对但做法不对"

### 原则六：内置验证循环与可观测性

一个好的 Skill 必须包含验证思路。在执行逻辑中加入验证循环：

- 最终输出前自检：字段完整？路径有效？格式正确？
- 用检查点确保每一步都真的做了
- 执行过程具备日志记录，支持调试分析和问题定位

```
5. 自检清单：
   - [ ] 所有必填字段是否已填充？
   - [ ] 输出路径是否存在？
   - [ ] 格式是否与模板一致？
   → 任一不通过，回溯修正
```

### 原则七：安全性与权限边界

Skill 具备真实的执行能力，必须考虑安全治理：

- 限制工具范围：Skill 只使用它需要的工具，不过度授权
- 敏感数据强制执行只读模式
- 外部操作（发消息、调 API、修改文件）需显式确认
- 防止提示注入和数据窃取风险

### 原则八：标准化输出与工程化结构

输出格式越明确，结果越稳定。四层分工：

| 层 | 职责 | 形式 |
|:---|:---|:---|
| **自然语言** | 判断与编排 | SKILL.md 核心流程 |
| **脚本** | 稳定执行 | scripts/ 确定性代码 |
| **模板** | 规范输出 | assets/ 模板文件 |
| **参考资料** | 补充细节 | references/ 规则文档 |

> 把输出当作**API 接口设计**——字段固定、类型固定、顺序固定，方便下游直接消费。

## 三、工程化落地规律（战术执行）

基于八大原则，在实际编写 Skill 时严格遵循以下九条规律：

### 规律一：Description 字段决定触发时机

告诉 Agent **什么时候使用**该 Skill，同时写中英文关键词。明确说明**什么时候不要用**。

```
✅ 好例子：
"将研究论文转化为学术演示文稿。当用户提供论文PDF并要求制作PPT时使用。
不要用于：普通文本转PPT、商业演示文稿、非学术内容。
Trigger: 论文转PPT, paper to PPT, 学术演示, academic presentation"
```

### 规律二：主文件保持清晰，细节按需加载

核心规则放在主文件（SKILL.md），场景细节、边界情况、完整示例放入子文件，让 Agent 按需读取。

> 主文件超过 200 行是危险信号——考虑拆分。

### 规律三：工作流必须编号

不编号 = 模型自由发挥 = 结果不可预测。编号清单是最便宜的确定性提升手段。

```
❌ 自然语言："你需要先读取文件，然后检查字段，最后写入输出"
✅ 编号清单：
1. 读取输入文件，校验 frontmatter 完整性
2. 根据 category 字段选择目标目录（决策树见 references/routing.md）
3. 生成输出内容，填入模板
4. 写入目标文件
5. 自检：确认文件存在且字段完整
```

> 复杂决策逻辑 → 用决策树或路由表，不要用自然语言描述分支。

### 规律四：写清楚默认行为

当用户没有给出某个参数时，Skill 必须知道默认怎么处理。这不是"限制灵活性"，而是"防止不吭声就跑偏"。

常见需要定义默认行为的场景：
- 输入为空时 → 报错并提示需要哪些参数
- 路径未指定时 → 使用规定的默认路径
- 格式未指定时 → 使用默认模板
- 冲突处理方式 → 保留双方内容，标记 `[待确认]`

### 规律五：规定输出格式模板

把输出格式当作 API 接口设计——字段名固定、类型固定、顺序固定。Agent 才不会再创作。

```
不是："输出一个包含标题和内容的 Markdown 文件"
而是：
---
title: "{{标题}}"
category: "{{分类}}"
source: "{{链接}}"
---
{{正文}}
```

### 规律六：规则必须有来源

每一条约束都应该能追溯到来源——官方文档、论文、课程、用户约定、或工程实践。不要让"我觉得"变成规则。

| 优先级 | 来源类型 | 示例 |
|:---|:---|:---|
| 1（最高） | 官方文档/API 规范 | Anthropic Skill 文档、Obsidian API |
| 2 | 论文/课程/权威方法论 | Nature Skills 设计模式、软件工程原则 |
| 3 | 工程实践验证 | 团队内部多次验证有效的模式 |
| 4 | 用户显式约定 | 用户明确要求的目录结构、命名规范 |
| 5（最低） | 最佳实践推断 | 业界公认但不一定有官方背书 |

> 不确定的规则标记 `[待验证]`，不要让猜测伪装成规则。

### 规律七：两种体量路线都可行

| 路线 | 适用场景 | 示例 |
|:---|:---|:---|
| **单文件（轻量）** | 简单规则、线性流程、单一操作 | 简单格式转换 Skill |
| **主文件 + 子文件（标准/重量）** | 复杂规则、多模式路由、方法论驱动 | 知识框架流水线 Skill |

选择一个路线后保持一致，不要混搭。

### 规律八：要有示例和测试用例

定义一个"优秀输出长什么样"的样例，用测试用例验证 Skill 是否真正有效。

```markdown
## 测试用例

### 用例 1：正常输入
输入：一篇包含完整 frontmatter 的文档
期望输出：移动到目标目录，frontmatter 补全所有必填字段

### 用例 2：缺失字段
输入：frontmatter 缺少 category 的文档
期望输出：报错，提示缺少 category 字段，不移动文件

### 用例 3：边界情况
输入：空文件或格式无法识别的内容
期望输出：报错并说明原因，不执行任何操作
```

### 规律九：中文用户需要专门章节

如果 Skill 面向中文用户，必须明确规定：

```markdown
## 语言约定
- 输入：接受中文和英文输入
- 术语处理：中文术语保留原文，首次出现附英文（如 前端控制器 Front Controller）
- 输出语言：默认中文，除非用户指定其他语言
- 文件命名：使用中文文件名（如 `粗加工处理器.md`）
```

## 四、最小必要结构模板（可复用规范）

基于以上原则和规律，提炼出标准化的 Skill 写作模板。这不是教条——而是**防止遗漏关键部分的基线**。写完一个 Skill 后，用此模板逐项对照：缺了哪个，就补哪个。

```yaml
---
# 1. YAML 门控：定义 Skill 的基本元信息
name: skill-name              # 唯一标识符，kebab-case
description: >
  简要描述该技能的功能以及何时该使用它。
  包含中英文触发关键词，并明确非触发条件。
  说明与其他 Skill 的区别。
license: MIT                  # 可选
agent_created: true           # AI 创建的标记
metadata:
  version: "1.0.0"
compatibility: 通用
---

# 2. 核心定位：说明此 Skill 解决什么问题、不解决什么
- 定位：...
- 边界：与 XX Skill 的区别在于...
- 类比：类似微服务中的 XX 模块

# 3. Default Stance：定义核心原则和禁止行为
## 默认行为
- 输入为空时：报错并提示需要哪些参数
- 未指定输出路径时：使用规定的默认路径
- 遇到冲突时：保留双方内容，标记 [待确认]

## 禁止行为
- 绝不删除源文件，只做复制或移动
- 绝不修改用户未提及的文件
- 绝不在没有显式确认的情况下发送消息或调外部 API

# 4. Workflow：编号说明任务执行顺序
1. 第一步：读取输入，校验完整性
2. 第二步：根据条件选择分支（决策树见 references/）
3. 第三步：生成输出，填入模板
4. 第四步：写入目标文件
5. 第五步：自检验证
   - [ ] 所有必填字段是否已填充？
   - [ ] 输出路径是否存在？
   - [ ] 格式是否与模板一致？
   → 任一不通过，回溯修正

# 5. Output Format：固定输出结构和字段
| 字段 | 类型 | 必填 | 说明 |
|:---|:---|:---|:---|
| field_a | string | 是 | 字段说明 |
| field_b | enum | 是 | 可选值列表 |
| field_c | markdown | 否 | 可选内容 |

# 6. Relative Files：说明不同情况应加载哪些子文件
| 文件 | 何时加载 | 内容 |
|:---|:---|:---|
| SKILL.md | 始终 | 核心流程、关键决策点 |
| references/routing.md | 多模式场景 | 路由决策树 |
| references/edge-cases.md | 遇到异常时 | 边界情况处理 |
| scripts/validator.py | 校验步骤 | 确定性校验脚本 |
| assets/template.md | 生成输出时 | 输出模板文件 |
| examples/good-output.md | 不确定输出格式时 | 优秀输出样例 |

# 7. Source Hierarchy：写明规则来源和优先级
| 优先级 | 来源 | 示例 |
|:---|:---|:---|
| 1 最高 | 官方文档/API 规范 | Anthropic Skill 文档 |
| 2 | 权威方法论 | 软件工程原则 |
| 3 | 工程实践 | 验证有效的模式 |
| 4 | 用户约定 | 用户要求的规范 |
| 5 最低 | 最佳实践推断 | 业界公认做法 |

# 8. 语言约定（面向中文用户）
- 输入：接受中文和英文
- 输出：默认中文
- 术语：首次出现附英文原文
```

## 五、级别分类

| 级别 | 判断条件 | 最少结构 |
|:---|:---|:---|
| 🟢 轻量 | 单一操作、无分支决策、规则 ≤ 5 条 | `SKILL.md`（含 YAML + workflow + output） |
| 🟡 标准 | 3-5 步流程、规则 > 5 条 | + `references/` 或 `examples/` |
| 🔴 重量 | 多模式路由、方法论驱动、多 Skill 组合 | + `assets/` + `scripts/` + `evals/` |

---

## 六、设计模式速览

- **Request Router**：SKILL.md 开头放路由表，Agent 先判断场景再走对应分支
- **Skill 组合（Pipeline）**：复杂流程拆成多个小 Skill，通过触发条件串联成流水线
- **Step-by-step 工作流**：编号清单写核心流程，详细展开放在 references/
- **Template-driven Output**：输出格式由模板文件定义，Skill 只需引用模板路径
- **Decision Tree**：复杂分支用决策树，不用自然语言描述 if-else

---

## 七、Skill 审查清单

写完或修改 Skill 后，逐项检查：

### 必查项（七要素完整性）
- [ ] YAML 门控：name、description 完整
- [ ] Description：中英文关键词 + 排除条件 + 与相关 Skill 的区别
- [ ] Default Stance：默认行为 + 禁止行为
- [ ] Workflow：数字编号，含自检步骤
- [ ] Output Format：字段固定、有模板/样例
- [ ] Relative Files：子文件加载时机明确
- [ ] Source Hierarchy：规则来源和优先级清晰

### 质量项
- [ ] 主文件是否控制在 200 行以内？
- [ ] 是否有测试用例和优秀输出样例？
- [ ] 面向中文用户时是否有语言约定章节？
- [ ] 不确定的规则是否标记了 `[待验证]`？

### 安全项
- [ ] 是否定义了工具使用范围？
- [ ] 外部操作是否需要显式确认？
- [ ] 是否禁止删除源文件？
