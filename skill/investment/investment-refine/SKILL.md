# 提炼执行器

---

## Default Stance

### 核心原则

- **直接执行**：读取原文后直接分析、创建条目、汇报结果，不需用户逐步确认。批量操作连续执行后统一汇报
- **分析即决策**：分析原文时内部完成归属层、分类、标签、质量判断，不输出方案报告等待确认
- **可读性优先**：正文保留原文的比喻、案例、推理链条和生动表达。用自然语言段落而非干巴巴的要点罗列
- **忠实原文**：可重组表达、优化结构，但绝不捏造、编撰、偏离原文事实。比喻和案例必须来自原文
- **简体中文产出**：框架条目正文一律用简体中文。若原始资源仍为繁体（粗加工遗漏），提炼时作兜底繁转简，仅字形转换、不改用词语气
- **标签来自标签体系，与文件夹分类互补**：标签捕捉文件夹无法表达的跨维度信息，允许跨分类引用（如投资心得文件可标分析框架标签）。市场/行业标签仅在内容确实仅限特定市场/行业时添加，通用心得不强制绑定。标签宁精勿滥，不自造标签
- **条目间关联**：仅指同源多条条目之间的逻辑关联，在执行汇报中标注关联方向；跨 vault 的关联备注在审查阶段处理。**提炼阶段不在文件中创建任何关联章节**——既不输出 `## 关联` 章节，也不输出空脚注占位。条目间关联的正式落地是审查阶段写入文末脚注区的关联脚注（`[^enhance-N]`/`[^complement-N]` 等，见 footnote-taxonomy.md）
- **模板驱动**：执行时每个条目必须使用对应分类的模板填写 frontmatter + 正文
- **参数全部由编排者传入**：缺参即报错

### 禁止行为

- 绝不在"我的"层创建或修改文件
- 绝不遗漏博主行的处理（如涉及已登记博主，必须同时更新博主档案）
- **绝不静默丢弃分类不明的言论**——分流时遇到 ①不属于任何既有 content_type、②定位模糊（多类型皆可/价值高但去向不明）的情况：**禁止丢弃、也禁止强行套类**，必须在执行汇报中单列「⚠ 待确认分类」一节（逐条附原文 + 不确定原因 + 候选建议），交用户裁决「**新增分类**（走 dict 字典流程，framework-rules #30 码值权威源）」或「**指定归属**」；裁决前不写入、不丢弃（细则见 refine-schema.md §六「分类不明处置」）
- 绝不将非投资内容放入"其他"层
- 绝不使用标签体系外的标签
- 绝不捏造、编撰原文没有的内容——比喻和案例必须来自原文
- **绝不臆造任何结构化字段值（2026-09-19 用户拍板：「严谨的材料收集师，不能有半点造假」）**：`sourceUrl`／标的名／股票代码／数据／日期／`replyTo` 等**一律照抄真实来源**（帖子留档 `post_history`、关联表、原文本身、可查证的一手资料），**禁止凭记忆手填或编一个"看起来合理"的值**——本条专治「提炼时臆造 sourceUrl 致 `post_history_id` 悬空、原文不可回溯」的事故。**缺就是缺、有就是有**：拿不准先查（留档→关联表→WebSearch），查无实据就在汇报里**如实标缺并说明原因**，绝不为凑齐字段而填假值、也不拿假值去触发落库钩子；落地脚本**按帖子 `id` 从 `post_history` 直接 SELECT `source_url`/`posted_datetime` 再传参**，**绝不肉眼把上一屏 pull 里的 URL 抄到下一条**（相邻帖极易串号——本轮两处错链即源于此），不事后补记。
- 绝不在粗加工/提炼时自动将未登记作者「补登」进博主控制台——未登记作者其条目归「其他」层，且**绝不就「是否补登」询问用户**（见 framework-rules #12）
- 绝不输出模板残留成分（`{...}` 花括号占位、`> 指引` blockquote、frontmatter 行内注释、全空表格占位行）——模板为纯结构骨架，产出文件不得含任何模板解释残留（见 footnote-taxonomy 禁止行为 #5）
- 绝不在正文末尾添加"来源+原文引用"blockquote——来源信息只写 frontmatter `source` 字段（见 footnote-taxonomy.md 禁止行为 #4）
- 绝不使用 `enhance`/`supplement`/`conflict`/`complement`/`data`/`date` 以外的脚注标签前缀（见 footnote-taxonomy.md 禁止行为 #1）

## Workflow

### 前置条件（由编排者保障）

- **常规路径**：输入来自 `工作区/原始资源/` 且 `status=待提炼`；**硬判定（#22）以文件物理位置为准，不看 `status` 值**——仍在 `工作区/粗制品/` 的采集件一律不得提炼（#29/#30 例外见下）。
- **例外路径（#29 帖子集，2026-09-12 改为「从 post_history 直提」）**：雪球帖子集原文已在采集时落 `post_history`，提炼从库内读取（MCP `post_history` `action=get`/`check`），**不经粗加工、不进原始资源、不读不产生 vault 文件**。
- **摘要帖不可提炼**（硬约束）：标「摘要」的帖内容残缺，一律跳过——它们按设计不入 `post_history`，故从库取原文时天然只有全文帖。

### 第 1.4 步：落库前置检查（2026-09-12 下沉）

写入前必过**八问**（有方向吗 / 信号具体吗 / 够短吗 / 正文干净吗 / `form` 填了吗 / 篇幅砍过头吗 / 新称呼落库吗 / 九项字段齐吗）与三份合法信号范例、服务端门禁清单——**完整表格见 `references/refine-schema.md` §七**。答错会被服务端拒写（`_validateSignal`/`form`/空壳/`sourceUrl` 硬门禁），返工成本高。

### 第 0.5 步：原文来源优先级（2026-09-11 新增）

提炼前若**手头没有原文**（采集产物已清理、只要补某一条、或某帖不在本批），**先查原文库**，不要直接重抓：

| 顺序 | 来源 | 工具 |
|:--|:--|:--|
| ① | **`post_history` 原文库（采集落点 + 提炼前原文；帖子集路径的默认也是唯一来源）** | MCP `post_history` → `action=get`（传 `url`）或 `action=check`（传 `blogger`+`from`/`to` 列清单） |
| ② | vault 原始资源文件（仅常规路径） | 常规读取 |
| ③ | 上两者都没有 → 才回采 | 按 `source_url` 单帖回采，**遵守 post-fetch `execution-guide.md` 的单帖限流**（≈0.7 req/s、405 退避 300s），回采后顺手 `post_history` `action=upsert` 落库 |

> `post_history` 的用途有二（2026-09-12 用户拍板）：① **提炼的原文来源**（帖子集路径直接从这里读，不再落 vault 文件）；② **避免重采**。它不参与归类判定、也不存提炼产物，提炼产物仍落 `statement`（六表 + 视图；言论行带 `post_history_id` 指回留档，方向是**言论表 → post_history**）。
>
> **留档保留 180 天（用户拍板，硬约束；2026-09-15 由 30 天放宽）**：post_history 是滚动窗口——**查不到是正常情况**，不是数据缺口、不是异常。因此：① 提炼仍应在采集后尽快做（逾期原文就不再留档）；② 查不到原文时按上表第 ③ 步回采即可（回采后顺手 `upsert` 落库，重新进入 180 天窗口）；③ 汇报里不得把「留档无记录」写成漏采或缺陷。

### 第 0.6 步：拿不准就进「待复核」队列，别猜（2026-09-12 用户要求）

用户原话：「显示你无法处理的需要我复核的帖子，这种帖子在下次审查的时候可以处理，并且内化规则，**让我以后可以不用再审核类似的帖子**」。提炼时遇到**规则没覆盖 / 两种归类都说得通 / 标的名认不出**的情况，**不许瞎猜、不许留空糊过去**，调 `MCP pending_decision action=add` 上报（看板「待复核」页在「审查」左边）：

- **上报什么**：归类边界拿不准（predict↔view、trade↔insight、是否算 chat）；标的名解析不出实体（`blogger_statement` 会自动报一类，其余补齐）；博主自造称呼/代号有歧义；时间存疑（原帖无日期、跨度异常）；规则确实没写到的新情况。**凡是置了 `is_review_required=1` 的，一律必须同时上报**（标记只是"这行曾被质疑过"的痕迹，裁决走待决策队列；只打标记不上报＝死信，用户看不见）——见 framework-rules #53。
- **怎么报**（硬要求）：`question` 一句话能独立看懂；**必须给候选 `options`**（`/` 分隔，让用户点一下就完事）；`excerpt` 放原文片段；能定位就带 `statementId` + `sourceUrl`；`kind` 用 `归类待定/标的名解析不出/称呼歧义/时间存疑/数据缺口/规则待定/其他`。
- **别重复问**：上报前先 `action=list`（可按 kind）搜一遍队列与既有答复，同一个问题只问一次；**规则里已经写明的自己判**（先查 `framework-rules.md` / `refine-schema.md` / `stock-mention-rules.md`），别把该自己判断的推给用户。
- **闭环**：用户的答复在**下一次提炼**里内化成规则（本 SKILL 第 0.7 步，framework-rules #49），所以**下批提炼先看一眼队列里的已答复项**——同类帖子按已有答复处理，不必再问。
- **用户可能直接给「删除」意见**（`verdict=delete`，形如「删除：纯情绪转述，没有判断」）：那是**删除指令 + 低质帖判据**（2026-09-12 用户明确「有的帖子质量不够，但是你提炼了」）。提炼侧要做两件事：① **落库前先比 `refine-schema.md` 的「用户删过的类型」判据表**，命中即不落库；② 已在库的同类帖子（自己提炼过的）**由本 SKILL 第 0.7 步按删除清单执行删除**（2026-09-15 起不再交审查）。

### 第 0.7 步：处理已裁决的待决策队列（提炼首步之二 · 必做；2026-09-15 从审查挪来）

用户原话：「**已决策的，跟着下一次提炼一起提炼掉，不要跟审核**」。**每次提炼开工前先清一遍队列**：用户答复过但还没落成规则的项（`status=resolved` 且 `internalized=''`）就是欠下的账，攒着不清＝同类问题会一直问用户。agent 侧走 `MCP pending_decision`：

1. `action=list, status=pending_internalize` → **已答复但规则还没落地**的项（本步核心工作）；
2. 逐条：按用户答复**修数据**（改归类/补标的名/改时间/补别名…）→ 把答复**内化成规则/案例**（落点四选一，见 framework-rules #49：`framework-rules.md` 条目 / `stock.aliases` / `mention_case` / `refine-schema.md` 细则）→ `action=internalize` 把落点写回 `internalized`；
2b. **`verdict=delete`（用户写了「删除：<理由>」）＝必须真的删**（2026-09-12 用户明确：「有的帖子质量不够，但是你提炼了，这种我就会在复核意见写上删除」）：
    - 取清单：`pending_decision(action=list, status=pending_internalize, verdict=delete)`；
    - 逐条 `blogger_statement(action=delete, id)`（买卖帖走 `blogger_trade delete`）→ `action=internalize` 写「已删除言论 #id + 规则落点」；
    - **必须把删除理由内化**：追加到 `refine-schema.md` 信息密度门槛的**「用户删过的类型」判据表**，并按判据回看同批/存量同类帖子一并处理；
    - **不许反问用户「确定要删吗」**、不许只改内容、不许跳过（理由已给＝已授权；删除不可逆但这是用户明确要求）。
3. 再看 `action=list, status=open`：**还没答的**不要替用户决定——在汇报里列出「待用户裁决 N 条」即可（含每条的问题与候选）；若发现某条其实规则已覆盖，改为 `action=resolve` 并写清依据（同时把规则落点写进 `internalized`）；
4. 汇报里写明结果：**「待决策：处理 N 条（内化 M 条 / 忽略 K 条），仍待裁决 J 条」**。

**只答不内化＝违规**：用户答一次是为了以后不再答同类问题，答复不进规则就等于让用户重复劳动（framework-rules #49）。

### 第一步：分析原文

读取原文全文（常规路径：`工作区/原始资源/` 文件；**帖子集路径：`post_history` 库内原文**，MCP `post_history` `action=get`/`check`），分析内容：

1. 判断每条内容的归属层（我的/博主/其他）和分类（分析框架/交易体系/投资心态/投资心得/个股/行业/宏观）
2. 标签来自标签体系（investment-framework/references/tag-taxonomy.md），允许跨分类引用；通用心得/心态不强制加市场/行业标签。**禁止裸标签（2026-08-17 全库体检强化）**：tags 必须挂一级分类前缀（如 `投资心态/心理偏误/后视偏差`、`分析框架/估值`），**禁止 `AI`/`泡沫`/`估值` 这类单层裸词**——tag-taxonomy 层级硬约束（最少二级、最多三级）；落库看板与写入文件 frontmatter 的 tags 必须一致
3. **检查库内关系（分层检索链 + 关键词决策规则，2026-08-17 用户确认）**：决定产物 新建/追加/互补 前，按优先级链检索库内——
   - **① 同作者同类分类**（最高优先）：读取该作者同分类下已有条目（如 `博主/雪月霜/分析框架/`），命中 → 追加/互补
   - **② 全库主题兜底**：未命中再按**关键词**扫全库（跨作者/跨分类，防重复建设——两位博主同主题时不得各建一份）
   - **③ 仍无 → 新建**
   - **关键词决策规则**：① 主关键词 = 候选产物名拆分（去虚词、拆并列词，取 2-3 个）② 次关键词 = 原文核心实体/概念（公司/行业/原文特有词，取 1-2 个）③ 合并去重共 3-5 个词；检索目标 = 库内条目**文件名 + 标题 + 标签**（不扫全文，全文噪音大）；命中任一主关键词 → 候选对比（追加/互补），仅命中次关键词 → 低权重候选，全不命中 → 新建
4. **归属层铁律**：作者必须在博主控制台（看板 MySQL blogger 表）已登记才能用「博主」层；未登记一律「其他」层，且 Agent 绝不自动补登、绝不就此询问用户（见 framework-rules #12）
5. **可验证判断提示（2026-08-14 新增）**：识别原文中的可验证判断/预测（如"未来两年跑赢""最低点在 X 时点""股息率锚定底部"），在执行汇报中提示用户"该判断可后续建分析档案做结果跟踪"（治 2026-08-14 审查发现的 59 条经验无验证载体——根因是分析档案/结果跟踪机制使用率极低，全库仅 2 个分析档案）
6. **同作者一致性预检（2026-08-14 新增）**：原文含明确规则/判断时，读取该作者**同类分类下已有条目**的核心判断句（交易体系看规则、方法论看适用场景、心态看纪律）——发现同一情境相反指令（如"绝不补仓" vs 已有"创新低加仓"），在汇报中提示潜在矛盾供用户裁决，**不自动修改已有条目**（治 C3 同作者自相矛盾；2026-08-14 审查发现 4 处同作者矛盾）

### 第 1.5 步：博主言论分流决策矩阵（2026-09-03）

雪球博主帖子**每帖只落一条言论**（2026-09-11 用户拍板），按**优先级顺序判定、命中即止**：**买卖记录 → 预测记录 → 研究 → 心得总结 → 观点 → 闲聊**（一帖多主题时取优先级最高者，其对象即 target）。**完整决策矩阵、优先级命中条件表、`predict` 判定三要素（含白酒易错例）、信号（stance）7 条判据与药神实例、标的代称还原、观点时间双时间判定、能成 wiki 的一刀切判据、落库铁律与查重 → 见 `references/refine-schema.md`「六、博主言论分流决策矩阵」**（判据权威源同 framework-rules #30）。

### 第二步：创建框架条目

**2.0 写入前预检（2026-09-11 事前门禁，硬约束）**：条目内容**先落临时文件，过预检再写入正式路径**——不合格当场改，不等全库事后回检：

```bash
python3 investment-framework/scripts/verify-format.py --preflight /tmp/draft.md
# 退出码 0 = 通过可写入；1 = 有问题（逐项修正后重跑）
```

预检覆盖（写入前拦截）：source 缺失/标量格式、`date` 字段越界、日期带引号、空标题、标题嵌段落、脚注孤儿、`## 来源`/空脚注残留、来源 blockquote、`{...}` 模板残留、`## 关联` 章节。

按分析结果直接执行：

1. 按归属层和分类确定文件路径

**写入硬约束**（wikilink 完整路径 / 个股带代码 / 无 `## 来源` 段 / 模板 section 全量 / frontmatter 字段顺序 / `star: false` + `delete:` 常驻 / 日期裸写 / 产出物去 emoji）——**完整清单见 `references/refine-schema.md` §八**，权威源为 `framework-rules.md` 对应编号。

2. 选择对应模板（从编排者传入的 templates）
