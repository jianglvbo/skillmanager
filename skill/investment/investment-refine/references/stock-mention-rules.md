# 个股提及与别名判定规则（关键词邻接 + 二元分类特征）

> 用途：提炼一条言论时，判断文中出现的词**是不是个股**、**指的是哪只股**，从而决定是否写 `statement_stock_rel`。
> 起因（2026-09-12 用户提出）：博主常写代称（寒武纪→「寒王」、中芯国际→「中芯h」、科大讯飞→「讯狗」、中远海控→「海控」），
> 而有些词**既是常用词又是股票简称**（美的、长江、中免、平安），机械匹配会把「美的房子」「长江后浪」误判成个股。
> 本文件给出**可执行的判定流程**：先看硬信号，再看邻接窗口，最后用二元特征打分，分数不足就不建关联。

## 一、三档判定流程（命中即止，逐档降级）

> **粒度（2026-09-12 硬规则）**：一律**按标点分句**独立判定，同帖多次出现各自算分——**禁止因为同帖某句命中就把整帖其它出现的同一个词也判正**。
> 反例（标准答案）：帖子「好美的风景，买点薯片来吃」「美的业绩不行，空调卖不出去」
> —— 第 1 句判**非个股**（形容词用法，N1）；第 2 句判**个股·美的集团**（F7：同句「空调」命中美的集团主营；邻接「业绩/卖不出去」属经营与产品类）。

### 第 1 档：硬信号（命中判「个股」，**但歧义词例外**，见下）

> **歧义词规则（2026-09-12 用户要求）**：别名命中后若该词在 **`dict(type='ambiguous_word')`**（本身也是常用词：美的/小米/平安/长江/中免…）
> → **不直接判正**，必须再过第 2 档邻接与 F7 产品词共现；只有专有代称（寒王/讯狗/海控）命中才免上下文直接判正。
| 硬信号 | 例 |
|---|---|
| 雪球标签写法 `$…$` | `$贵州茅台(SH600519)$`、`$中远海控(601919)$` |
| 名称/代号后紧跟括号代码 | `腾讯控股(00700)`、`寒武纪(688256)` |
| 库内命中：`stocks.name` 精确等于该词 | 名字本身已是登记的个股名 |
| 库内命中：`stocks.aliases` 含该词（逗号分隔） | 别名库里的「寒王」「讯狗」 |

> 组合代号 `$名称(ZH123456)$` **不是个股**（雪球组合），按 `<框架>/framework-rules` 处理：只留 `target` 文本。
> 指数/ETF/基金（`$恒生指数$`、`$沪深300$`、`$中概互联ETF$`）也不是个股。

### 第 2 档：关键词邻接（**先分句，再分级**；2026-09-12 v2.1 修正）

> **先按标点（，。；！？\n）切小句，只在「该别名所在的小句」内找证据**——跨小句不算。
> 反例（血的教训）：`好美的风景，买点薯片来吃` 若按 8 字窗口，`买点薯片` 的「买」会落进窗口，把「美的」误判成美的集团。
> 分级（同一小句内）：**紧邻（±2 字内）动作/经营词 = 强证据 2 分**；同小句出现 = 弱证据 1 分；产品词（F7）同小句 = 2 分。
| 邻接类别 | 词表 |
|---|---|
| 买卖动作 | 买/买入/加仓/减仓/清仓/卖出/割/建仓/止盈/止损/抄底/补仓/仓位 |
| 价格与估值 | 股价/价格/估值/PE/PB/市值/目标价/单价/元/港元/美元 |
| 持仓与账户 | 持仓/成本/浮盈/浮亏/套住/解套/底仓 |
| 交易语境 | 开盘/收盘/涨停/跌停/换手/成交量/回调/破位/新高 |
| 市场标签 | A股/港股/美股/科创板/创业板/主板/北交所/港股通 |
| 同现代码 | 同句出现 `\d{5,6}`、`[A-Z]{1,5}\d{1,5}`、`ZH\d+` |
| **经营与产品**（2026-09-12 补） | 业绩/营收/净利/毛利/销量/渠道/库存/产能/主营/提价/降价/亏损/毛利下滑 + 具体产品词 |

### 第 3 档：二元分类特征打分（每项 1 分，**≥2 分判个股；=1 分判存疑；0 分判非个股**）

**正向特征（是个股时容易成立）**
| # | 特征（布尔） | 判定依据 |
|---|---|---|
| F1 | 词形像公司简称 | 2–4 字，或以 股份/集团/控股/科技/医药/电力/银行/能源/重工 结尾 |
| F2 | 首次出现带全称，后续用简称 | 同一帖里先出现全称再出现该简称（简称→全称映射） |
| F3 | 与已知个股共现 | 同句/同段出现其它已登记个股名或代码 |
| F4 | 与已知行业共现 | 同句出现库内行业名（半导体/白酒/电解铝…） |
| F5 | 博主历史惯用 | 该博主历史言论里该词高频出现且都伴交易/估值语境 |
| F6 | 句子主语是博主行为 | 「我在」「我买」「我持有」「我的仓位」+ 该词 |
| **F7** | **产品/主营词匹配**（决定性，2026-09-12 补） | 该词在 `stocks.keywords`（主营/产品关键词）里的词与**同句**共现，如「美的…空调」「宁德时代…电池」 |

**负向特征（不是个股时容易成立）**
| # | 特征（布尔） | 判定依据 |
|---|---|---|
| N1 | 通用词/形容词用法 | 「美的」（漂亮的）、「长江」（江河）、「平安」（平安无事）、「小狗/隔壁」（口语） |
| N2 | 行业/主题词 | 词本身在 `industries` 或行业通用词表（半导体、光模块、创新药） |
| N3 | 指数/ETF/组合 | 含 指数/ETF/基金/组合，或 `ZH` 代号 |
| N4 | 人名/机构/平台名 | 邻接「老师/大佬/雪球/东财/券商」，或本身就是博主名 |
| N5 | 时间/数量词 | 邻接「年/月/日/倍/个点/%」，且无买卖词 |
| N6 | 纯代号且不可还原 | 小写拉丁短名（`cww`）且全帖无线索（服务端门禁也会拦） |
| N7 | 泛指集合 | 邻接「们/这些/那些/一批」，如「这些个股」「大佬们」 |

**打分判定（v2.1：负向一票否决优先）**
- **先看负向**：命中 N1（`好/真/太/多/美景/风景` 这类程度副词+名词/形容词用法）→ **直接判非个股，不再累加正向**（否则「买点薯片」的「买」会把分数顶上去）
- 得分 = 正向命中数 − 负向命中数
- **≥2 → 判个股**（歧义词必须满足「紧邻动作词」或「同小句产品/经营词 ≥2」才算 ≥2）：写 `statement_stock_rel`，并确保该股有行业关联（`stock_industry_rel`，缺则按邻接的行业词补建）
- **=1 → 存疑**：不建关联，把该词原样留在 `target` 文本，并置 `review_required=1`，进「待确认」清单
- **≤0 → 判非个股**：不做任何关联（不要为了"看起来完整"硬塞）

## 二、别名库维护（判定的沉淀物）
1. **来源**：买卖帖的 `target_alias`（提炼时留痕的原帖代称）→ 回填 `stocks.aliases`（逗号分隔）
2. **新增别名时**：只加**该股专属**的代称（寒王、讯狗、海控）；**不要把通用词加进别名**（美的、平安、长江、中免）——它们同时也是常用词，进了别名库会让「好美的风景」直接命中个股。通用词只能靠第 2/3 档上下文与 F7 判。
2b. **产品/主营词放 `stocks.keywords`，不放 `aliases`**（2026-09-12 新增列）：`keywords` 存该股主营与产品关键词（如 美的集团 → `空调,暖通,家电,小天鹅,库卡`），只用于 **F7 同句共现判定**；`aliases` 存专有代称。二者分工不同，不要混。
3. **别名冲突处理**：若一个词同时像两只股的简称（如「中免」→ 中国中免 vs 中免集团），以**同帖硬信号（代码/`$…$`）**为准；无线索则按存疑处理
4. **复现检查**：每批提炼后，对存疑词复盘一次；确认的补进别名库，否证的记入下方清单

## 三、常见误判清单

> **案例进库，文档只留范例（2026-09-12 用户提出「规则会一直迭代、量会很大」）**：
> 本节只保留最具教学价值的几条；**新增案例一律写进数据库**：
> ```
> stock_alias { "action":"case-add", "sentence":"原文片段", "value":"句中称呼",
>               "stockName":"正确归属（skip 时省略）", "verdict":"link|doubt|skip",
>               "reason":"命中了哪条规则/被哪条否决", "source":"refine|review|user" }
> stock_alias { "action":"case-list", "value":"美的" }   # 查询已有案例（可做回归）
> ```
> 存放表 `mention_case`（sentence/alias/stock_id/verdict/reason/source），可被工具查询、可做回归测试。
> 这样文档不会随案例无限膨胀，而**判定算法与机制**留在这里（那是几乎不变的部分）。

（出现即按负向特征处理；完整案例库见 `mention_case`）
| 词 | 为何易误判 | 正确处理 |
|---|---|---|
| 美的 | 「美的风景/美的房子」是形容词；「美的业绩/美的空调」是美的集团 | **v2.1 标准答案（三句连测）**：`好美的风景，买点薯片来吃` → skip（N1 程度副词+名词，一票否决）；`美的业绩不行，空调卖不出去` → link（同小句经营词 3 个 + 产品词 空调）；`寒王的业绩不及预期` → link（专有代称免上下文）。**注意**：v2.0 用 8 字窗口会把第 1 句的「买点薯片」算成证据而误判 link——必须分句+分级 | **两例句已定为标准答案**：`好美的风景，买点薯片来吃` → 非个股（N1）；`美的业绩不行，空调卖不出去` → 美的集团（F7 同句「空调」+ 经营类邻接）。通用词不进别名库，全靠上下文 |
| 长江 | 长江电力简称，也是江河 | 需邻接「电力/水电/长电」或硬信号 |
| 中免 | 中国中免简称，也是机构名的一部分 | 看是否带代码或 `$…$` |
| 平安 | 平安无事 / 中国平安 | 邻接「保险/银行/集团」才算 |
| 小单 / 大光 / 隔壁 | 博主行话（小单不动如山、隔壁被禁） | 不是个股；留在正文 |
| 狗狗 / 猫猫 | 口语化代称 | 除非别名库已登记，否则不建关联 |
| 这些个股 / 大佬们 | 泛指集合 | 不建关联 |
| 通胀 / 利率 | 宏观概念，**不属于市场** | 不建 `statement_market_rel`（用户明确：通胀不属于市场） |

## 四、与落库动作的对应
| 判定结果 | 落库动作 |
|---|---|
| 个股（≥2 分或硬信号） | `statement_stock_rel` + 该股 `stock_industry_rel`（缺行业则补） |
| 存疑（=1 分） | 不建关联；`target` 保留原词；`review_required=1` |
| 非个股（≤0 分） | 不建关联（词留在正文本就够） |
| 博主 | **每条言论必挂** `statement_blogger_rel`（用户明确：言论可以没有个股/行业/市场，但一定有博主） |
| 行业 / 市场 | 命中库内名称（`industries.name` / `markets.name`）才建对应 rel |

## 五、维护节奏
- 每批提炼后跑一次「存疑词清单」复盘 → 确认的补 `stocks.aliases`，否证的补进第三节清单
- 别名库与行业关联由**服务端写入**（`blogger_statement` 落库时同步），不要手改数据库

## 六、别名与规则的迭代机制（学到的必须落库；2026-09-12 用户要求）

> 用户原话：「提炼或者审查发现我的复核有什么，修正后比如美的指的是美的集团，你要记得把它更新到 stock 的 aliases，并且更新对应的规则……
> 后续如果知道或者我复核后你知道了，你要记得迭代规则。」→ 因此**知识不能只留在对话里**，必须落库 + 改规则。

| 触发时机 | 谁执行 | 必须落库 / 更新 |
|---|---|---|
| 提炼时遇到未登记的称呼（如 寒王=寒武纪、讯狗=科大讯飞、小米=小米集团） | 提炼环节 | 调 `stock_alias(action=add, stockName, value)` 写入 `stocks.aliases`；顺手 `set-keywords` 补该股主营/产品词 |
| 提炼时判断该称呼**同时也是常用词**（美的/小米/平安/长江/中免） | 提炼环节 | 调 `stock_alias(action=mark-ambiguous, value=该词)` → 落 `dict(type='ambiguous_word')`，此后该词命中必须过上下文 |
| 审查发现误判（如「好美的风景」被挂成美的集团） | 审查环节 | ① 修正言论关联（`blogger_statement(action=update)` 改 target/或删除错误 rel）② 查因：缺歧义标记就 `mark-ambiguous` ③ 把案例写进本文第三节误判清单 |
| 用户复核（看板左滑「这条应是…」）确认了某个称呼的归属 | 复核处理流程（`console_statement_review`） | 落实修正后**必须**回填别名（同上第一/二行），并把结论写进本文档；不允许只改那一条言论就结束 |
| 发现规则本身判错（新语境、新反例） | 提炼/审查/用户任一方 | **直接改本文件**（误判清单 + 特征表），并同步到四个 skill 根 |

**三条铁律**
1. **别名 ≠ 通用词**：`aliases` 可以收录常用词（美的/小米），但**必须同时登记为歧义词**，否则「好美的风景」当场误判；两件事永远一起做。
2. **落库优先于记忆**：任何口头/对话里确认的映射，当场调 `stock_alias` 落库；只在对话里说过 = 下一步就会忘。
3. **规则是活文档**：每修一个误判，本文件第三节清单要加一条（词 + 为何易误判 + 正确处理），规则随数据一起长。

## 七、存储与容量（2026-09-12 用户提问后定案）

| 内容 | 存在哪 | 为什么 |
|---|---|---|
| 别名（称呼：寒王/讯狗/美的/小米） | `stocks.aliases`（**每股一行**，逗号分隔） | 天然按股分片；500 股 × 5 个别名也才 2500 条，工具一条查询全取回；与个股生命周期绑定 |
| 主营业务/产品词（空调/思元/SU7） | `stocks.keywords` | 同上，且 F7 判定只按句内共现取用 |
| 歧义词（本身是常用词） | `dict(type='ambiguous_word')` | 「与常用词同形」是**词的属性**，不是某只股的属性；登记一次全局生效 |
| **判定案例（会一直长）** | **`mention_case` 表** | 每修一个误判就多一条；进库后可用 `stock_alias(case-list)` 查询、可做回归测试；避免文档无限膨胀 |
| **判定算法**（分句/分级/否决/阈值） | **本文件** | 几乎不变的「程序」，给人读也给 agent 读 |
| 机制（何时该落库、谁来做） | 本文件 §六 | 同上 |

**为什么不用单独一个 JSON 文件**：那会成为**第二个真相源**——库里一份别名、文件里一份，两边迟早不一致（用户反复强调过「一个东西不许存两处」）。MySQL 本身就是结构化存储，工具与看板都能读，JSON 文件在并发写、备份、查询三方面都更差。

**容量判断**：别名与产品词的增长是**行内**增长（每股一行、几十字符），不会让任何一张表变大；真正会无限增长的是「案例」和「误判教训」，所以那两类**一律进 `mention_case`**，md 只留算法 + 机制 + 少量范例（当前 5 条）。
