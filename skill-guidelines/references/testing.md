# 真实提示词验证

> 创建与重大修改后的验证环节。静态自检不替代本环节——skill 的错误大多不在「写了什么」，而在「会不会触发、照不照做」。

## 轻量验证（默认，必做）

1. 第一步：写 2–3 条测试提示词——
   - **应触发 1–2 条**：带真实路径、列名、口语甚至错字，像真人打字（「~/Downloads/报表最终版.xlsx 里 C 列是收入，帮我加个利润率列」）
   - **不应触发 1 条**：near-miss 最值钱——共享关键词但实际要的是别的东西（CSV 分析 skill 的负例：`写个脚本把 csv 每行传进 postgres`——涉及 csv，其实是 ETL）
2. 第二步：测触发——新会话投给 Agent，看是否加载本 skill；不应触发的确认没触发
3. 第三步：复盘输出与 trace（不只看结果）——
   - 输出缺什么、错什么
   - trace 出现绕路、反复重读、堆临时脚本 = 过约束或指令含糊的信号 → **删**，不是加
   - 漏步骤、自由发挥 = 指令缺失或含糊 → 补判定规则与正反例
4. 第四步：回改 → 重跑 → 与用户复盘，直到过关或改动不再产生收益

## 重量验证（可选，关键 / 高频 skill）

- 用例存 skill 目录下 `evals/evals.json`：`{prompt, expected_output, files?, assertions?}`，先 2–3 条即可，跑完第一轮再补断言
- **with/without 对照**：每条用例跑两遍（无 skill 基线 / 有 skill），隔离上下文（子代理或新会话）；断言评分 PASS 必须附证据，机械可验的用脚本判
- 断言审读：**双过**（基线也过）的断言删掉——不反映 skill 价值；**双挂**的先修断言或用例；**只过有 skill 的**断言才是价值所在
- 改进三信号：失败断言（补缺口）+ 人工反馈（结构问题）+ trace（为什么错），汇总后改 skill，别为单条用例打补丁（skill 面向的是没见过的输入）
- 描述触发率优化（触发不稳时）：20 条查询（10 正 10 负）每条跑 3 次算触发率（0.5 为阈值），60/40 切 train/validation 防过拟合，最多 5 轮、按验证集最优取舍

## 改写已有 skill 时

- 改前快照旧版当基线，改后用同一批提示词对照新旧输出，确认没把对的改错
- 触发条件变了，重跑负例确认边界没被改宽
