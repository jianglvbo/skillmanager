# 工程规律

## 规律一：四步递进，逐层增强

Skill 不是一次性写完的，而是递进式建构。每一步都能独立运行：

```
第一步: SKILL.md（元数据 + 指令）        → 写了菜名和做法
第二步: + Reference（认知卸载）          → 附上食材清单
第三步: + Script（执行优于模拟）         → 配了验菜工具
第四步: + Dynamic Context（环境感知）    → 菜谱自动看冰箱
```

## 规律二：Description 决定触发

含中英文关键词，明确什么时候不要用。

## 规律三：主文件短，细节下沉

主文件 ≤ 200 行。场景细节/边界/示例 → references/。
Reference = 给 AI 读的"外存"，不堆在"工作内存"（主文件）。

## 规律四：Reference 读 vs Script 做

| 类型 | 操作 | Token 消耗 | 适用场景 |
|:---|:---|:---|:---|
| Reference | AI 读取全文进入上下文 | 消耗 Token | 规范、规则、需要理解的文档 |
| Script | AI 执行但**不读**代码，只看输出 | 极省 Token | 格式验证、数据校验、文件操作 |

关键决策：这个任务靠 AI"理解"就能做对吗？→ 写 Reference。这个任务需要精密计算且不允许出错？→ 写 Script。

## 规律五：工作流必须编号

```markdown
❌ "先读文件，再检查，最后输出"
✅
1. 第一步：读文件校验
2. 第二步：选分支（见 references/routing.md）
3. 第三步：生成输出
```

## 规律六：写清楚默认行为

输入为空？路径未指定？格式未指定？冲突怎么处理？每项都要有答案。

## 规律七：输出格式模板化

不写「输出一个 Markdown」，而是给出完整 frontmatter 模板。

## 规律八：规则有来源

| 优先级 | 来源 |
|:---|:---|
| 1 | 官方文档 / API 规范 |
| 2 | 权威方法论 |
| 3 | 工程实践 |
| 4 | 用户约定 |
| 5 | 最佳实践推断 |

不确定的标记 `[待验证]`。

## 规律九：两种体量都可行

| 体量 | 结构 | 适用 |
|:---|:---|:---|
| 轻量 | 单 SKILL.md | 线性流程、<5 条规则 |
| 标准 | SKILL.md + references/ | 多模式、方法论驱动 |
| 重量 | SKILL.md + references/ + scripts/ | 需要精密计算验证 |

## 规律十：有测试用例

定义「正常输入 → 期望输出」「缺失字段 → 期望报错」「边界 → 期望行为」。

## 规律十一：中文用户专节

规定输入语言、输出语言、文件命名、日期格式。
